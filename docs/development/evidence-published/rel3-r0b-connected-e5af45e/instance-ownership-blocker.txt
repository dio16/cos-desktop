MP-R0B / native GUI verification: instance-ownership blocker investigation

Symptom: every launch of target/debug/cos-desktop.exe exits with code 2 and prints
  COS Desktop instance ownership unavailable; startup refused
This blocks any window-based check (foreground handoff, UI Automation reads, connected baseline).

What was probed, with results:
  1. No cos-desktop process is running (Get-Process cos-desktop returned nothing).
  2. A freshly created isolated LOCALAPPDATA, pre-populated with cos-desktop/, still refuses startup
     with the same message; the default LOCALAPPDATA refuses identically.
  3. The lock file %LOCALAPPDATA%/cos-desktop/desktop.instance exists, is a regular file, and can be
     opened with ReadWrite access and ReadWrite sharing, twice concurrently.
  4. A directory handle to %LOCALAPPDATA%/cos-desktop opened with GENERIC_READ, share mode 3 and
     flags 0x02200000 (BACKUP_SEMANTICS | OPEN_REPARSE_POINT) succeeds (handle obtained, error 0).
  5. LockFileEx exclusive on desktop.instance succeeds (returns true, error 0).

Conclusion: the main operating-system operations the guard relies on succeed when executed outside the
application - directory handle, lock-file open with sharing, exclusive lock - yet the application still
reports the ownership guard as unavailable. This is not a whole-guard verification: the probes did not
cover create_dir_all, the metadata() checks on the directory and the lock file, the reparse-point
attribute rejection, or the Rust File::try_lock result. The cause is therefore not identified, and this
is recorded as an unresolved blocker with those branches untested, not as an environment limit and not
as a pass. Native GUI verification stays blocked until it is identified.

Consequence for MP-R0B: connected CPU and working-set numbers remain NOT_MEASURED; the connected
measurement path and its refusals stand as the implementation result.
