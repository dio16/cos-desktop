W1〜W5で成立した内容:

W1:
実WIC materialization前のbudget admission。

process-memory観測、bounded worker、
stage hold、cancel/timeoutの停止帰属。

実Bgr565のformat admissionと画素検証。

W4:

orientation/ICC metadata取得と、
画素・colour transform適用証明の分離。

一方、W2が示した3-worker memory値は
single collection windowの非原子的な合計である。

それは実際のprocess countersの観測だが、
WIC internal scratch、allocator reservation、
真の同時allocation peakではない。

W6ではW2を単に再実行するのではなく、

- codec差
- source寸法差
- 同時worker数差
- before-OnLoad / after-OnLoad段階差
- repeated collection windows
- sample欠落・worker終了時の証拠境界

どの範囲まで定量的に比較可能かを前進させることである。

W6で実測されたprocess countersを、
decoder内部allocationへ帰属させてはならない。

不変条件:

10. 未承認のnumeric SLO、decoder採用、
    production concurrency policyを決定しない。

11. W1〜W5のSOURCE・Native・Gate証拠は不変。

7. FixtureとNative matrix
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

新しいdeterministic fixtureを生成する。

原則として次の3種類を使う。

- PNG RGB 8-bit
- BMP24
- BMP Bgr565

寸法クラス:

- 256×256
- 1024×1024

合計6組のcodec/size組合せを基本集合とする。

Bgr565はW3と同じbitfield admission条件を使用する。
Bgr555対照をBgr565に混入させない。

ピクセルパターンには、
全単色だけでなく、繰り返しのある
非一様なdeterministic patternを使用する。

ランダムなOS entropyには依存しない。

fixture単位で記録する。

- fixture_id
- generator identity
- container
- encoded bytes
- encoded SHA256
- source dimensions
- source pixel format
- channel depth/storage bpp
- logical row bytes
- decoded requirement
- BGRA32 requirement
- declared scratch requirement
- independent RGBA oracle digest

入力サイズと全decoded要求量をchecked arithmeticで
計算する。

必須Native実験:

SET A — Single-worker scaling
6 codec/size組合せ。
after_onload boundaryで1 workerずつ観測。

SET B — Three-worker cohort
256×256の3 codecを同時に起動し、
after_onload boundaryで観測。

SET C — Three-worker cohort
1024×1024の3 codecを同時に起動し、
after_onload boundaryで観測。

SET D — Before-OnLoad cohort
同じ3 codecのbounded cohortを使用し、
before_onload boundaryで観測。

SET B/C/Dについて少なくとも2回の反復を行う。

最大worker数:
3

最大case数:
24

標準matrix:
6 singles + 4〜6 cohorts相当を上限内で構成。

各cohortのcase identityとsize/formatを固定し、
反復間で入力バイトが同一であることを確認する。

実行時に必要なメモリが安全上限を超える場合、
対象cohortを縮小するかREFUSEDとする。

上限を引き上げて成功を作ってはならない。

8. 実測観測点とsampler
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

W2の実装を基準に、
実Windows System.Diagnostics.Process countersを使用する。

必須:

- PID
- Process.StartTime UTC ticks
- 実行ファイルidentity
- worker source identity
- WorkingSet64
- PrivateMemorySize64
- 観測window開始/終了
- timestamp clock domain
- process alive before/after
- observer command exit
- capture byte length
- observation completeness

利用可能なら追加:

- PeakWorkingSet64

ただし、PeakWorkingSet64は
process lifetimeのOS counterであり、
WIC decoder固有scratchでも
真の同時allocation peakでもない。

OS counterやAPIが利用できない場合、
その値はNOT_MEASUREDとする。

W2の既存samplerは、
同じcollection window内で
各processを逐次読み取る。

W6はこの実測を時間系列へ拡張する。

各cohortについて
少なくとも3つの有効collection windowを目標とする。

各windowには:

- sampler_start
- sampler_end
- QPC開始/終了とfrequency
- parent monotonic開始/終了
- per-worker sampling order
- per-worker counter value
- summed counters
- sample gap
- complete/partial status

を保持する。

重要:

異なるworkerのcounter取得は
原子的なsnapshotではない。

window合計は
DERIVED_WINDOW_SUMと分類する。

複数window中の最大値は
MAX_OBSERVED_WINDOW_SUMとする。

「true concurrent peak」
「allocator peak」
「reserved memory」
「decoder scratch peak」
という名称へ変換しない。

別々のprocess lifetime peakの合計を
同時peakと呼ばない。

取得期間にprocessが終了した場合、
そのwindowを完全な成功標本として扱わない。

途中失敗のwindowを無言で削除せず、
失敗と欠落を記録する。

10. Resource authorityと上限
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

既存W2/W5のbounded executionを維持する。

基本上限:

- worker数: 最大3
- 全case数: 最大24
- worker deadline: 最大45秒
- global deadline: 最大300秒
- max dimension: 1024
- max pixels: 1,048,576
- decoded bytes: 最大4MiB
- declared scratch: 最大8MiB
- output file: 最大16MiB
- owned work root: 最大64MiB
- trace: 最大128 records / 128KiB
- captured stdout/stderr: 各64KiBを上限とする
- report: 最大8MiB
- complete/incomplete sample windows合計: 最大32
- observed private-byte bound: 768MiB

以上はW2のbounded実験制約を引き継ぐ
実験上限であり、製品のratified SLOではない。

samplerが追加work root容量を必要とする場合、
上限を自動的に増やさない。

3標本を期限内に取得できなかった場合は
取得数と不足理由を残す。

不足を埋めるためにworkerを無期限に保持しない。

WIC内部からの実予約情報は
今回の利用可能APIにない。

したがって:

explicit_known_reservations_bytes:
NOT_MEASURED

decoder_internal_scratch_peak:
NOT_MEASURED

actually_proven_peak_concurrent_allocation:
NOT_MEASURED

を維持する。

新しい予約APIや独立allocator計測手段が
必要と判明した場合は、必要なAPIと権限を
DESIGN_BLOCKEDとして記録する。

今回、製品側に仮の予約管理APIを追加しない。

11. Stop / timeout / cleanup
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

W2のclosed stop state machineをそのまま使用する。

有効なcancel/timeoutの証明には:

- child alive at request
- exit_before_request=false
- hold_established=true
- last stageが指定boundary
- termination actually issued
- kill_errorなし
- reap confirmed
- non-zero exit
- requested/observed/exited整合
- successful output未公開

を要求する。

単なるkill()成功、
自然終了とのrace、
OnLoad中の推定停止は
confirmed cancellationにしない。

観測中にworkerが自然終了した場合、
実際のterminal outcomeを保持する。

unverified_raceをcancelledへ昇格しない。

sampleに失敗しただけで
workerを成功終了したとみなさない。

workerが残存する場合、
所有processのみをboundedに回収する。

他processや過去work rootを操作しない。
