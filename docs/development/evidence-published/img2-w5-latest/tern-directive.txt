2. タスク選択理由
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

実装計画上、MP-IMG2のhard prerequisitesは:

- MP-IMG1
- MP-SEC3

既存の限定成果:

W1:
実WICのmaterialization前admission。

W2:
実WIC bounded decode、process memory観測、
operator boundary holdに限定した停止帰属。

W3:
実Bgr565 format admissionと独立RGBA raster照合。

W4:
実WIC ROI出力とfull-frame予算維持、
true partial/sequential/tiledとの能力分離。

残存するDC-MP-IMG2の主な要件:

- codec別のorientation handling
- ICC/profile/colour handling
- decoder internal scratch
- actual allocation/reservation
- true peak concurrent bytes
- cancellation granularity
- 16K capability
- true region/sequential/tiled decode
- codec比較とadoption decision

今回は、このうちorientationとICC/profileの
実WIC capability分類を単一sliceとして選択する。

理由:

- DC-MP-IMG2に既に明記された要件である
- IMG1/SEC3以外のhard prerequisiteを追加しない
- 既存のWIC probeとbounded fixtureを再利用できる
- 新decoder dependencyやunsafe/FFIを必要としない
- RuntimeとGPUを変更せず実験できる
- 既存のDecode Exitを縮小しない

なお、MP-IMG2全体のdecoder採用や
full Decode Exitを今回承認するものではない。

3. W5の目的
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

実Windows WICについて、以下を独立に確認する。

A. SOURCE METADATA

入力に格納されたorientation情報とICC/profile情報を、
decoder結果と混同せず取得・分類できるか。

B. DECODED RASTER

実WICのdecoded outputが、
orientation/profile metadataによって
どのような変化を受けるか。

C. TRANSFORM APPLICATION

orientation補正やICC colour conversionが
実際に適用されたことを証明できるか。

D. ADMISSION BOUNDARY

不正なorientation、profile metadata、
過大なmetadata、矛盾した宣言が、
無制限allocationや成功扱いにつながらないか。

E. CAPABILITY CLASSIFICATION

codec/containerごとに、
metadataの存在・取得・解釈・適用・未測定を
別フィールドとして表現できるか。

重要な区別:

「EXIF orientationを読めた」
≠
「画素を正しく回転した」

「ICC profileを取得できた」
≠
「正しい色変換を実施した」

「WICがdecodeに成功した」
≠
「表示色・表示方向が正しい」

「source profileが存在しない」
≠
「sRGB profileが実際に埋め込まれていた」

W5では、以上の誤認定を防止する。

7. WIC metadata probe
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

既存wic_probe.ps1へ、
明示的opt-inのmetadata observationを追加する。

CLI名称は既存規約に整合させること。

通常実行の意味は変更しない。

opt-in無しの場合:
- 既存引数
- exit code
- result schemaの既存フィールド
- output bytes
- legacy behavior
を維持する。

W5 metadata observationでは、
実WICの宣言値と取得経路を記録する。

最低限:

- container codec
- decoder identity
- decoder/cache mode
- source dimensions
- source pixel format
- frame dimensions
- metadata availability
- orientation tag presence
- orientation raw value
- orientation interpreted meaning
- ICC/profile presence
- profile byte length
- profile fingerprint
- colour context availability
- decoded output dimensions
- decoded output pixel digest
- explicit transform request
- observed transform outcome
- materialization stage
- failure reason

source metadataとdecoder outputは独立の欄にする。

ただし、値の取得・解釈・画素への適用は

勝手にorientation=1と補完しない。

ICC/profileについても、
存在しないこと、取得できないこと、

unknownの値を成功扱いしない。

8. Fixture generation
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Python標準ライブラリを優先する。

小さくdeterministicなfixtureだけを生成する。

推奨する実験セット:

A. OrientationなしのPNG

B. MetadataなしのBMP24

C. Orientation=1の小型画像

D. Orientation=3の小型画像

E. Orientation=6の小型画像

F. Orientation=8の小型画像

G. Invalid orientation value

H. Conflicting metadata declarations

I. ICCなし

J. 有効なICC profileを含む入力

K. 不正またはtruncated ICC payload

L. 許可上限を超えるmetadata payload

実装上は、
小型の非圧縮TIFF等を使用して
orientation tagを直接制御してよい。

JPEG/EXIFを使用する場合は、
元encoded byte sequence、EXIF tag、
metadata変更範囲を記録する。

ただし、
JPEGのdecoded RGBAが絶対的に正しいという
主張は今回行わない。

ICC profileを含むfixtureには、
出典・再配布可能性・実バイトdigestを記録する。

実際の有効profileを確保できなければ、
そのpositive caseをNOT_RUNとして保持する。

不正ICCだけのテストで
正しいICC colour conversionを証明してはならない。

ユーザー画像や非公開画像は使用しない。

各fixtureには:

- fixture ID
- generator identity
- container
- encoded bytes
- SHA256
- dimensions
- source raster
- metadata field offsets
- orientation value
- ICC payload identity
- expected behavior
- bounded case limit

を記録する。

9. Orientation verification
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

実WICによるmetadata読み出しを確認する。

次の観測を分離する。

1. tagが存在するか
2. tagの値を読み出せるか
3. 値を仕様上どう解釈するか
4. decoderが自動適用したか
5. decoded dimensionsが変化したか
6. decoded pixelsが変化したか
7. display transformが必要か

製品UIの表示方向は変更しない。

可能な限り、
同じencoded rasterに対して
orientation metadataだけを変えたfixtureを用いる。

比較には:
- source pixel order
- output dimensions
- pixel coordinates
- deterministic marker pattern
を使用する。

lossless fixtureについては
独立RGBA oracleと全画素比較する。

90度/180度回転に対応する座標写像は
WIC実出力から逆算せず、
独立oracleで定義する。

WICがmetadataを無視する実装なら、
「metadata read verified」
「orientation application not observed」
と分けて記録する。

WICによる自動適用を観測した場合も、
他codec全体への適用を推定しない。

意図しない二重回転を検出する負例を含める。

10. ICC / Colour handling verification
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

以下の状態を区別する。

profile_present
profile_readable
profile_bytes_verified
profile_applied
colour_transform_verified

ICC profileの取得だけでは
profile_applied=trueにしない。

profileの有効性判定だけでは
colour_transform_verified=trueにしない。

色変換を証明する場合は、
独立に定義した期待色値、
変換条件、
出力色空間、
許容誤差、
適用前後の値を必要とする。

色変換参照結果を作成できない場合、
colour_transform_verified=NOT_VERIFIEDとする。

「BGRA32へのformat conversion」
と
「ICC colour conversion」
を同一視しない。

WIC内部のcolour pipelineやscratchが
直接観測できない場合はNOT_MEASUREDとする。

今回の必須成果は、
ICC/profileのmetadata取得能力と
colour conversionの証明状態を分離することである。

ICC変換の正確性を
未証明のまま製品能力へ登録してはならない。

11. Admissionとsecurity boundary
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

metadata読み出しが、
無制限allocationやfull decodeを
暗黙に誘発しないことを検証する。

少なくとも次の上限を適用する。

- encoded input size
- source dimensions
- max pixels
- full-frame decoded requirement
- conversion bytes
- declared scratch
- metadata capture bytes
- output bytes
- worker deadline
- trace bytes
- report bytes

既存W1/W2/W3/W4の上限を緩和しない。

metadata inspectionが既存WIC API内部で
どの程度allocationするか不明な場合は、
それを証明済みと扱わない。

取得API自体が安全なpre-materialization経路で
呼べると確認できない場合、
既存のfull-frame admissionを先に適用する。

解析不能なmetadataで、
無制限fallback decodeを行わない。

不正なmetadataの分類:

- malformed
- unsupported
- not_readable
- absent
- not_verified

を区別する。

仕様上有効だが未対応のprofileを
corruptと偽ってはならない。

また、不正metadataが存在するというだけで
すべてのcodecをunsupportedと判断しない。

実際のsource/decoderの応答に基づき分類する。

operator holdなしのkillを

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

既存WICのICC metadata取得と
orientation分類実験は続行してよい。

権限不足はAUTHORITY_BLOCKED、
未実行はNOT_RUN、
測定不能はNOT_MEASURED、
証明不足はNOT_VERIFIEDとして記録する。

未証明の能力をPASSへ変換しない。
